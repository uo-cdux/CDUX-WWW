Introduction

Alaska is the research cluster for CDUX. This document provides basic information about Alaska, as well as how to make use of it. Here is the front and back view of Alaska.


Hardware and Configurations

  • Head node
    • Two Xeon E5-2667v3 CPU ( 16 cores @ 3.2GHz)
    • 256 GB DDR4 memory
    • 6 HDD in RAID5 configuration, ~18TB
    • 2 SSD in RAID0 configuration, ~2TB
  • Cluster nodes (4 in total)
    • One Intel Xeon E5-1650v3 CPU ( 6 cores @ 3.5GHz)
    • 32 GB DDR4 memory
    • 1 SSD, ~256 GB
  • Hostnames
    • The head node has hostname Alaska.
    • The cluster nodes have hostnames cn1, cn2, cn3, cn4.
  • Filesystem
    • $HOME is accessable from all nodes. This is the main storage space.
    • /flash_buffer is accessable from all nodes. This is a fast I/O space. It's capacity is limited to 2TB though.
    • /opt is accessable from all nodes but read-only. It keeps a few libraries and packages to be used by environment modules.
    • /Research_Data is accessable from all nodes but read-only. It keeps a few data sets that might be useful for our group. (Note: this disks experiments the btrfs file system with transparent compression. As a result, this disk could hold a little more data than its real capacity: 2TB.)
  • 10Gb ethernet connection among these nodes.
  • Ubuntu 14.04 LTS on all machines.


Login

  • Authenticated users use their ix usernames and passwords to log onto Alaska:
    • ssh < username >@alaska.cs.uoregon.edu
  • Users need to first log onto Alaska, and then from Alaska to log onto cluster nodes (cn1 - cn4).
  • Logging onto the cluster nodes can be as simple as ssh cn1, for example.


Environment Modules

  • Modules are used to manage environment variables on Alaska. In fact, they secretely manipulate your environment variables such as $PATH, $LD_LIBRARY_PATH, etc.
  • Usage of Modules on Alaska is similar to this post from Nersc.
  • Modules are grouped into different versions of compilers. It is strongly recommended to use the same version of compiler for your code, dependency libraries, and MPI implementation.
  • The combinations of compilers and MPI implementations are a little tricky on Alaska. Here is a list of valid combinations:
    • Not loading any modules (you're using gcc-4.8 and openmpi-1.6);
    • Only loading gcc-4.8/openmpi-1.8 (you're using gcc-4.8 and openmpi-1.8);
    • Loading both gcc-5.3/gcc-5.3.0 and gcc-5.3/openmpi-1.10.2 (you're using gcc-5.3 and openmpi-1.10).


Launch MPI jobs

  • Before you run MPI jobs across multiple nodes, please make sure you have completed the following tasks:
    • Have set up authentication keys to enable passwordless login for all compute nodes (a tutorial could be found here).
    • After the above step, you basically have both your private key (e.g. id_rsa) and public key in your ~/.ssh folder. Don't panic, your private key is ONLY visible to you by default.
    • Manually logged onto all the nodes, so the machines keep each other's fingerprints.
  • Alaska has OpenMPI installed. Instead of using a job scheduler to allocate resources, here we use a text file to specify where to run a job: hostfile.
    • A sample hostfile can be found at: /opt/hostfile.
    • A hostfile is passed into mpirun through the --hostfile option. For example: mpirun -n 32 --hostfile hostfile ./my_program .


GPU Computing with CUDA

  • An Nvidia Tesla K40 GPU is installed in the cn4 node. You can access it by logging onto cn4.
  • An Nvidia Geforce 610 card is also installed in the cn3 node. Though CUDA capable, this card is probably only fast enough for debugging.
  • Nvidia Profiler (nvprof) and Nvidia Visual Profiler (nvvp) are good tools to profile your CUDA program. Note nvvp requires X11 window to run.


Utility Programs

These utility programs are available from the headnode, Alaska, and/or certain cluster nodes if specified. Some of them require X11 to use.

  • latex: pdflatex, etc. (cn1)
  • eog: eye of gnome image viewer. (X11)
  • mupdf: (super fast) pdf viewer. (X11)
  • qpdfview: pdf viewer. (X11)
  • meld: beautiful visual diff tool. (X11)
  • fldiff: fast visual diff tool. (X11)
  • retext: markdown viewer/editor. (X11)
  • gnuplot: making plots from data. (X11)
  • ghex: gnome hex editor. (X11)
  • w3m: command line html viewer.
  • imagemagick: image manipulator.
  • nvprof: nvidia profiler. (cn4)
  • nvvp: nvidia visual profiler. (cn4, X11)


Q&A

  • Q: Alaska seems pretty heavy loaded with little CPU resource left. What should I do?
    • A: Try one of the cluster nodes (cn1 through cn4). Your programming environment is expected to be the same as on Alaska, plus you have a good chance to occupy that node by yourself!

  • Q: I set up LD_LIBRARY_PATH to point to a custom directory on the head node. However, other nodes still have trouble finding the runtime libraries when I invoke my program with MPIRUN. What can I do?
    • A: Use -x option with MPIRUN. MPIRUN takes a -x option to export a specified environment variables to the remote nodes before executing a program. For example, mpirun -x LD_LIBRARY_PATH -n 32 ./my_program .

  • Q: What should I do when I need a specific python package?
    • A: Use pip. You can even specify where to install a package using the --target option. For example, pip install --target=/path/to/my/python/directory package_name .

  • Q: The disk seems to be too slow for me. What can I do?
    • A: You can move the I/O-heavy task to the solid state drives of Alaska. There are two possibilities. First is to use /flash_buffer, which is globally accessable from all nodes with ~2TB capacity. Second is to use /local_buffer, which is local in respect to cn1 through cn2 with ~180GB capacity each.
